In exception2.cpp, the reason you're seeing multiple destructor calls is because your catch blocks are catching
the exceptions `by value` rather than by reference.


When you catch an exception by value (e.g. catch(A a)), C++ creates a temporary copy of the thrown exception object.
The implicit copy constructors are being called silently.

for exceptoin2.cpp:
Case: Input 0 - (Throwing A)
    1. throw A(); : A temporary exception object of type A is created in memory.
        Output: A Constructor

    2. catch (A a): The exception matches this block. C++ creates a local variable a inside the catch block by
        copying the temporary exception object. 
    
    3. Execution: The code inside the catch block runs.
        Output: caught A.
    
    4. End of catch block: The local variable a goes out of scope and is destroyed.
        Output: A destructor (Destructor 1: the copied object)

    5. Exception cleanup: C++ destroys the original temporary exception object created by the throw() statement.
        Output: A destructor (Destructor 2: the original thrown object)

        ---- The exact same mechanism applied for int input 2 / Throwing D ----


Case: Input 1 (Throwing C - The "Strange" case) 
    This is a little complex case since it involves inheritance and `Object Slicing`. C inherits from B.

    1. throw C(); : A temporary exception object of type C is created. Because C inherits from B, the base
        class is constructed first.
        Output: B Constructor
        Output: C Constructor
    
    2. catch (B b): A thrown `C` object is perfectly valid to be caught as a `B` object. However because 
        you catch by value, C++ creates a local variable `b` of type B. It "slices off" the C part of the 
        object and only copies the B base sub-object into `b`.

    3. Execution: The catch block executes
        Output: caught B 
    
    4. End of Catch block: The local sliced variable `b`(which is strictly of type B) goes out of scope and
        is destroyed.
        Output: B destructor (Destructor 1: the sliced local copy)

    5. Exception cleanup: C++ destroys the original, full C temporary exception object.
        Destruction happens in the reverse order of construction (Derived, then Base)
        Output: C destructor (Destructor 2: the derived part of the original object)
        Output: B destructor (Destructor 3: the base part of the original object)


The Fix: 
    To prevent unnecessary copying, double destruction, and object slicing, standard C++ practice dictates 
    that you should "always throw by value and catch by reference(usually const reference)"

    That is what I did in the exception2_1.cpp

===========================================================================================
    Exceptions in C++ break the normal stack rules on purpose.
        If the exception object were created on the local call stack of f(), it would indeed be destroyed
        when f() exits, leaving nothing for the `catch` block to receive.

    The "Exception Space"

        When you execute throw A();, the C++ compiler does not place the temporary object on f()'s local stack. 
        Instead, it allocates this object in a special, hidden memory area managed by the C++ runtime (often
        called the exception space).
        Because this lives in this special runtime-managed space, it survives the destruction of f()'s stack frame.

    Actual Program Flow
    What happens behind the scene when an exception is thrown:
    
    1. The Throw: throw A(); is called. The C++ runtime allocates memory in the hidden exception space and 
        constructs the original A object there.

    2. Stack Unwinding: The runtime immediately reports f() and starts tearing down the call stack. Any local
        variables inside f() (and inside the try block) are destroyed. The original exception object is 
        safely preserved in the exception space - is not on any stack.

    3. catch block initialization: The runtime finds catch (A a). It uses the original object in the 
        exception space to initialize your local variable a. Because you caught by value, it copies the
        original object into a.

    4. Catch Block Execution: Catch block code runs and prints `caught A`

    5. Catch Block Ends: The local variable a goes out of scope and is destroyed, printing the first 
        `A destructor`.

    6. Exception Cleanup: The catch block is now completely finished. The C++ runtime determines the 
        exception has been fully handled, so it finally destroys the original object sitting in the 
        hidden exception space, printing the second A destructor.


If C++ destroyed the original object before the `catch` block ran, catching by reference ( catch (const A& a))
would be impossible because the reference would point to dead memory. By keeping the original object alive
in the exception space until the very end of the catch block, C++ guarantees that the exception data 
remains perfectly valid for as long as the handler needs it.
