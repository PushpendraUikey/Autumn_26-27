# 27th July 2026 — Design Pattern: Chain of Responsibility

## The pattern (GoF, behavioural)

> **Intent:** *Avoid coupling the sender of a request to its receiver by
> giving more than one object a chance to handle the request. Chain the
> receiving objects and pass the request along the chain until an object
> handles it.*

The client sends a request to the **first** handler and doesn't know which
handler will end up dealing with it. Each handler either **handles** the
request or **forwards** it to its *successor*.

| Role | Job |
|---|---|
| **Handler** | Interface for handling requests. Optionally implements the link to the successor |
| **ConcreteHandler** | Handles the requests it is responsible for, and forwards the rest |
| **Client** | Sends the request to the first handler in the chain |

```
Client ──▶ Handler1 ──successor──▶ Handler2 ──successor──▶ Handler3 ──▶ (end)
             handle or forward        handle or forward       handle or drop
```

**Consequences (GoF):**
- ✅ Reduced coupling: the sender doesn't know the receiver.
- ✅ Flexible: handlers can be added, removed or reordered at runtime.
- ❌ **Receipt isn't guaranteed.** A request can fall off the end of the
  chain unhandled.

Related patterns: Chain of Responsibility is often used with **Composite**,
where a component's parent acts as its successor.

### `design_ChainOfResponsibility.cpp`: GoF help system
- `HelpHandler` is the base class. It stores `_successor` and a `_topic`,
  and its `HandleHelp()` forwards the request to the successor by default.
- The chain is **Button → Dialog → Application**:
  - Each one checks `HasHelp()`.
  - If it has a help topic, it offers help. Otherwise it delegates with
    `HelpHandler::HandleHelp()`.
  - `Application` is the end of the chain.
- `Widget` uses its **parent widget as the successor**, which links back to
  Composite.
- This is reference code only: it **has no `main()`** (it compiles but
  doesn't link), and the "offer help" bodies are empty.

### `chainOfResponsibility_27thJul26.cpp`: generic pipeline
- `Handler<T>` has a public, non-virtual `handle()` that calls the protected
  virtual `process()`, then forwards the result to `next_`.
  - That structure is the **Template Method** idiom: the base class fixes
    the order of steps, and subclasses supply the step itself.
- `Pipeline<T>` links the handlers inside its constructor. Clients **never
  call `setNext()`**, and an empty list throws `invalid_argument`.
- Successors are held as `shared_ptr`, so ownership is automatic.
- The concrete handlers `T1`…`T8` are generated by a `DEFINE_HANDLER(NAME, EXPR)`
  macro.
- Output (both start from 5):
  - A: `5 → 6 → 18 → 15 → 25`
  - B: `5 → 2 → 2 → 4 → 16`
- **Difference from GoF:** here *every* handler processes the request and
  passes it on, like a pipeline or filter chain. In classic GoF, a handler
  **either** handles the request **or** forwards it, so at most one handler
  deals with it.

### `combinotoricsOfPolymorphicHierarchies.cpp`: the board assignment
- **Problem:** handlers `H1..H3` × transforms `G1..G3` should give all
  **A×B = 9** behaviours *without* writing 9 subclasses.
- **Solution:** composition.
  - `Handler` holds a `shared_ptr<Transform>`, which is the `*P` arrow on
    the board.
  - It is set at runtime with `assignTransform()`.
  - Only **A+B = 6 classes** are needed. A new `G4` works with every
    handler automatically.
  - This is the **Bridge** idea: prefer composition over inheritance.
- Output with input 5: 9 different results, for example
  `H1×G1 → 106`, `H2×G3 → -25`, `H3×G3 → 100`.
