DNS Security Extension (DNSSEC) were developed to provide origin authentication and integrity protection for DNS data by using digital signatures. 

These digital signatures can be verified by building a chain of trust starting from a trust anchor and proceeding down to the particular node in the DNS.

DNSSEC uses Key tags to efficiently match signatures to the keys from which they were generated. 
RRSIG RRs contain a Key Tag field whose value is equal to the Key Tag of the DNSKEY RR that was used to generate the corresponding signature.

This document specifies how security aware DNS resolvers that perform validation of their responses can respond to certain queries in a manner that allows an agent performing the queries to deduce whether a particular key for the root has loaded a given key into its trusted-key store. These tests can be used to determine whether a certain root zone Key Signing Key (KSK) is ready to be used as a trusted key, within the context of planned root zone KSK roll. 

If a browser or operating system is configured with multiple resolvers, and those resolvers have different properties (for example one performs DNSSEC validation and one does not), the sentinel test described in this document can still be used. 


Sentinal Mechanism in Resolver
    Two special labels are used:
    -> root-key-sentinel-is-ta-<key-tag>
    -> root-key-sentinel-not-ta-<key-tag>

These labels trigger special processing in the validating DNS resolver when the responses from authoritative servers are received. Labels containing "root-key-sentinel-is-ta-<key-tag>" are used to answer the question, "Is this the Key Tag of a key that the validating DNS resolver is currently trusting as a trust anchor?"

Lables containing "root-key-sentinel-not-ta-<key-tag>" are used to answer the question, "Is this the Key Tag of a key that the validating DNS resolver is *not* currently trusting as a trust anchor?"

Preconditions:
    The DNS response is DNSSEC validated.
    The result of validation is "Secure".
    The Extension Mechanisms for DNS (EDNS(0)) Checking Disabled (CD) bit in the query is not set.

    The QTYPE is either A or AAAA.
    The OPCODE is QUERY.
    The leftmost label of the original QNAME (the name sent in the Question Section in the original query) is either "root-key-sentinel-is-ta-<key-tag>" or "root-key-sentinel-not-ta-<key-tag>".

    If any of this preconditions is not met, the resolver MUST NOT alter the DNS response based on the mechanism in this document.
